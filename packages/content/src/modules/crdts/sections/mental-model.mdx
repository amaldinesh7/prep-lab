The single idea you need to internalize before reading any CRDT code is _strong eventual consistency_ (SEC). Everything else — algorithms, papers, library APIs — is a way to achieve it.

## The promise

A system is strongly eventually consistent if, whenever two replicas have received the same set of updates, they are in the same state. Order of arrival does not matter. Duplicates do not matter. The replicas do not need to coordinate. They just need to have seen the same events.

That's the contract. Read it again — the order doesn't matter is the surprising part. "Eventually consistent" databases like DynamoDB promise convergence given enough time, but the order in which writes are applied determines the final state and you typically need a coordinator to break ties (last-write-wins by timestamp). "Strong" eventual consistency removes both: convergence is deterministic _and_ requires no coordinator.

## The math (just enough)

To get SEC, your merge function has to be three things. Don't memorize the words — internalize the shapes.

**Commutative.** `merge(a, b) === merge(b, a)`. If two updates arrive in either order, the result is the same. This kills the timeline problem. There is no "first" or "second" update — they're a set.

**Associative.** `merge(a, merge(b, c)) === merge(merge(a, b), c)`. Grouping doesn't matter. You can batch updates, replay them piecewise, fold them in chunks — same answer.

**Idempotent.** `merge(a, a) === a`. Applying the same update twice is the same as applying it once. This is the unlock for unreliable networks: you can re-send updates without worrying about double-counting, because the receiver collapses duplicates for free.

Together these three properties define a _semilattice_ — a structure where you can always compute a unique "least upper bound" of any two elements. State-based CRDTs are literally implemented as semilattices; you'll see this in the next section. Op-based CRDTs get to the same place by being commutative under causal delivery.

## A toy example: the G-Counter

The smallest CRDT that captures the whole idea is the grow-only counter (G-Counter). It's a counter that goes up, never down.

The naive implementation — a single integer — does not work. Two replicas each increment by one, then merge. Whose value wins? Both. So you'd want `max(a, b)`, but then two increments collapse to one. So you'd want `a + b`, but then merging a replica with itself doubles it (not idempotent).

The CRDT version: each replica owns a slot in a map keyed by client ID.

<Code lang="ts" file="g-counter.ts">{`type GCounter = Record<string, number>; // clientId -> count

const merge = (a: GCounter, b: GCounter): GCounter => {
  const keys = new Set([...Object.keys(a), ...Object.keys(b)]);
  const out: GCounter = {};
  for (const k of keys) out[k] = Math.max(a[k] ?? 0, b[k] ?? 0);
  return out;
};

const value = (c: GCounter) => Object.values(c).reduce((s, n) => s + n, 0);

// Client "alice" increments locally
const inc = (c: GCounter, clientId: string): GCounter => ({
  ...c,
  [clientId]: (c[clientId] ?? 0) + 1,
});
`}</Code>

Walk through the properties:
- **Commutative:** `max(a, b) === max(b, a)`. Yes.
- **Associative:** `max` is associative. Yes.
- **Idempotent:** merging a replica with itself: `max(x, x) === x`. Yes.

The trick is that each client only ever writes to its own slot. Concurrent increments don't fight — they live in different fields. Merge takes the per-slot max, then `value` sums everything.

This is the entire blueprint. Every CRDT is a more elaborate version of "shard the data so concurrent writes don't overlap, then merge with a structure-aware operation that satisfies the three properties."

## Why "no central coordinator" is the magic

The hidden payoff of SEC: there is no place in the system that has to be online for progress to happen. Every replica can accept writes locally and merge later. The server (if there is one) is a relay, not an authority. Three consequences:

1. **Offline-first comes free.** Your client made twenty edits on a flight? Sync them when reconnected; the merge is correct.
2. **Peer-to-peer works.** Two clients can sync directly over WebRTC or Bluetooth without a server in the loop.
3. **The server can crash without losing edits.** As long as some replica has the data, it survives. This is why local-first products are so resilient.

The cost is structural: not every data type maps to a CRDT cleanly. Counters, sets, maps, ordered text — yes. Foreign-key relational consistency, balanced-budget accounting, anything where you actually need a global view to decide — no. We'll come back to this in the tradeoffs section.

## Two CRDT flavors

There are two ways to implement strong eventual consistency, and you'll see both terms in any CRDT codebase.

**State-based CRDTs (CvRDTs).** Replicas gossip their entire state. The merge function (a lattice join) combines two states into one. Convergence is a property of the lattice — easy to reason about, expensive on bandwidth.

**Operation-based CRDTs (CmRDTs).** Replicas broadcast individual operations. Receivers apply each op locally. Convergence requires that ops are commutative _and_ that they're delivered with respect to causal order — i.e., if op B was made knowing about op A, every replica must see A before B.

Both deliver the same end guarantee. They make different tradeoffs on the wire. The next section is about that.
