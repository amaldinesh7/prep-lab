<SectionHeader kind="gotcha" number={6} title="Production gotchas" />

Every team running TSR in production hits these. They're not bugs — they're the consequences of how the framework works. Knowing them saves an afternoon each.

## 1. Generated tree drift on file moves

`routeTree.gen.ts` is regenerated by the Vite plugin while dev is running. The plugin watches `src/routes/` for changes. If you move a file outside the dev server (a rebase, a `git mv` in a stopped shell, a teammate's PR), the generated tree is stale until Vite re-scans.

Symptoms:
- `"Route not found"` runtime errors on a route that obviously exists
- TS errors about missing exports from `routeTree.gen.ts`
- `<Link to="/posts">` suddenly stops autocompleting

The fix: restart the dev server, or run the standalone generator. Most setups add an npm script:

<Code lang="json" file="package.json">{`{
  "scripts": {
    "routes:gen": "tsr generate",
    "routes:watch": "tsr watch"
  }
}`}</Code>

CI lint should run `tsr generate` and check `routeTree.gen.ts` is up to date — otherwise a PR can pass typecheck locally but break main because the generated file wasn't committed.

## 2. SSR is opt-in — TSR is client-first

TSR renders in the browser by default. If you `view-source:` a TSR app you get a one-line `<div id="root"></div>` shell. That's fine for dashboards. It's not fine for marketing pages, OG cards, or pages crawlers care about.

If you need SSR, you have three options:

1. **TSR Start** — the official full-stack framework. Newer, less mature, but the right answer if you're going TSR + SSR.
2. **Separate marketing site** — keep TSR for the app, ship the marketing pages from Astro, Next, or plain HTML on a different subdomain. Most B2B startups end up here.
3. **Prerendering** — tools like `vite-plugin-prerender` snapshot a few key routes at build time. Workable for low-page-count public surfaces.

Don't try to bolt SSR onto a pure TSR app. The hand-rolled `renderToString` setups all break on hydration mismatches sooner or later.

## 3. Code-splitting and lazy routes — turn it on, but know what it does

`autoCodeSplitting: true` (in the Vite plugin) is the right default. It splits every route's component into its own chunk and lazy-loads on navigation. Loaders stay in the main bundle (because they need to run before render).

Two surprises to plan for:

**A flash of nothing on first navigation.** The chunk has to download. Solve with `<Route pendingComponent={Skeleton} pendingMs={300}>` — only show the skeleton after 300ms, otherwise the navigation feels instant.

**Loaders in the main bundle inflate the entry chunk.** If your loader imports a heavy library (date-fns, lodash, a parser), that import lands in the main bundle. Audit with `vite-bundle-visualizer`. Move heavy logic into the component, not the loader.

For routes you _know_ are rarely hit (admin panels, billing settings), you can explicitly mark them with the `lazy` API to bundle them separately even from the loader:

<Code lang="tsx" file="src/routes/admin.lazy.tsx">{`import { createLazyFileRoute } from "@tanstack/react-router";

// The "lazy" file is split; non-lazy route metadata still goes in admin.tsx.
export const Route = createLazyFileRoute("/admin")({
  component: AdminPanel,
});

function AdminPanel() {
  return <div>...</div>;
}`}</Code>

The pattern: `admin.tsx` holds the route definition (loader, search schema), `admin.lazy.tsx` holds the component. The component chunk is lazy; the loader is eager. Worth it only for genuinely heavy admin/billing/settings panels.

## 4. Router context typing — the silent type drift

`context` is the dependency-injection slot for loaders. You declare its shape on the root route:

<Code lang="tsx" file="src/routes/__root.tsx">{`import { createRootRouteWithContext } from "@tanstack/react-router";
import type { QueryClient } from "@tanstack/react-query";
import type { Auth } from "../lib/auth";

interface RouterContext {
  queryClient: QueryClient;
  auth: Auth;
}

export const Route = createRootRouteWithContext<RouterContext>()({
  component: RootLayout,
});`}</Code>

Then in `createRouter`:

<Code lang="tsx" file="src/main.tsx">{`const router = createRouter({
  routeTree,
  context: {
    queryClient,
    auth: undefined!, // populated later via RouterProvider's context prop
  },
});`}</Code>

The landmines:

- **`context` on `createRouter` must include every key**, even ones you'll inject later. `undefined!` is the canonical placeholder. If you forget a key, TS yells; if you cast around it, loaders blow up at runtime when they read the missing key.
- **`beforeLoad` can extend context**, and downstream loaders see the extension typed. But the extension only flows _downward_ — sibling routes don't see it. A common bug: you set `context.user` in `_authed.beforeLoad`, then try to read it from a public route. Compile-time fine if you're not careful with types; runtime `undefined`.
- **`RouterProvider`'s `context` prop replaces, not merges.** If you pass `context={{ auth }}` you lose `queryClient`. Always spread:

<Code lang="tsx" file="src/App.tsx">{`<RouterProvider router={router} context={{ ...router.options.context, auth }} />`}</Code>

## 5. Strict mode + scroll restoration

TSR ships a scroll restoration component you need to render explicitly. In React 18 strict mode, components mount twice in dev. If you put `<ScrollRestoration />` inside `__root.tsx`'s component and your scroll behavior is flaky, that's why — it's listening twice in dev only. Production is fine. Don't chase it in dev.

## 6. The "Route not found in tree" error

This one looks scary, fixes the same way 90% of the time:

```
Invariant: Route not found for path "/posts/$postId"
```

Causes, in order of likelihood:
1. `routeTree.gen.ts` is stale — restart Vite or run `tsr generate`.
2. The file's `createFileRoute("...")` string doesn't match the filename's URL. (The plugin usually rewrites this for you, but only if Vite is running.)
3. You renamed the file and forgot to update `<Link>` references — typecheck would have caught this if your CI runs it.

Don't `rm -rf node_modules` for this. Restart Vite first.

<Callout kind="gotcha">
  The single worst gotcha: a stale `routeTree.gen.ts` after a rebase, a file move, or a teammate's PR. Symptoms include type errors that don't make sense, "Route not found" at runtime, and `<Link>` autocomplete going blank. Fix: restart Vite. Prevent: CI step that runs `tsr generate` and fails if the working tree changes. Add this to your project before the second engineer joins.
</Callout>
